# Документация предметной области

Как engineering-скиллам использовать документацию предметной области этого репозитория при изучении кода.

## Перед изучением прочитайте

- **`GLOSSARY.md`** в корне репозитория.
- **`docs/adr/`**: ADR, которые касаются области, где вы собираетесь работать.

Если каких-то из этих файлов нет, **продолжайте молча**. Не сообщайте об их отсутствии и не предлагайте создать их заранее. Скилл `/domain-modeling` (вызывается через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их по мере того, как термины и решения действительно формулируются.

## Структура файлов

Репозиторий с одним контекстом (single-context):

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-slot-generation-in-api.md
│   └── 0002-postgres-for-bookings.md
└── apps/
    ├── api/
    └── web/
```

## Используйте словарь глоссария

Когда в результате вашей работы упоминается понятие предметной области (в заголовке задачи, предложении по рефакторингу, гипотезе, названии теста), используйте термин так, как он определён в `GLOSSARY.md`. Не подменяйте его синонимами, которых глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет, это сигнал: либо вы придумываете язык, которым проект не пользуется (пересмотрите), либо это реальный пробел (отметьте его для `/domain-modeling`).

## Сообщайте о конфликтах с ADR

Если результат противоречит существующему ADR, скажите об этом явно, а не переопределяйте молча:

> _Противоречит ADR-0007 (генерация слотов в API), но стоит пересмотреть, потому что…_
